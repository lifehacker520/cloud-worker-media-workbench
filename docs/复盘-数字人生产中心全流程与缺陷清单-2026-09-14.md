## 二、缺陷 / Bug 清单（按对「批量」目标的杀伤力排序）

| 级别 | 缺陷 | 现象/证据 | 建议 |
|---|---|---|---|
| **P0** | **云 GPU 抢占**：按量计费关机即释放 GPU，开机可能被他人占满 | **今晚实测**：F55 机空闲 GPU=0，开机被拒（提示克隆实例/无卡模式/等待） | 生产必须选①包年包月独占 ②自有服务器 ③开机前探测+克隆实例兜底。否则批量任务随时中断 |
| **P0** | **无自动重试编排**：批次内某条失败后，需人工点「重试」 | 今晚 r3 因 4 进程并发被挤崩，靠人工重跑成功 | 批次级「失败自动重试 N 次」+ 并发上限=1 的串行执行 |
| **P1** | **并发争用**：同一实例可被多个 run.py 并行占用，互相拖慢/挤崩 | 实测 4 进程并行 → 单条 212s（独占时 99s）；1 条崩溃 | Worker 侧加文件锁/队列；或平台侧全局串行 |
| **P1** | **轮询可能取到旧文件**：启动前未彻底清理 + 未校验文件新鲜度 | 实测出现过 0.288s「假成品」（旧残留文件被匹配） | 启动前删除目标文件 + 轮询时校验 mtime/size 变化 + 时长阈值（mediaChecks 已校验 >0.5s，需前置到轮询判定） |
| **P1** | **数据双轨**：单条快捷路径 `generate-real` 与批次 runner 路径并存，前者不写 model_run/quality_report | S7 遗留；S8-01 已记录未合并 | 让 generate-real 也登记 model_run，或 UI 只保留批次路径 |
| **P2** | 音色槽位需人工在控制台创建一次（不能纯 API） | 多员工规模化时每账号一次手工 | 评估批量建槽/或换支持纯 API 复刻的供应商 |
| **P2** | 字幕无自动切句（需 ASR） | `burnSubtitles` 需外部时间轴 | 接 ASR（火山/Whisper）生成时间轴 |
| **P2** | 缺少真实成本可见性 | `usage` 只有条目/成败，无时长/字数/调用次数与预算告警 | 用量端点补成本字段 + 阈值告警 |
| **P2** | 孤儿进程清理缺失 | 实例上曾出现 4 个并发 run.py，无自动回收 | Worker 启动前 pkill 同类 + 记录进程表 |
| **P3** | 两条导出路径（release-drafts vs 内容包）语义重叠 | 并存，使用者不知以哪个为准 | 产品确认合并方向 |

## 四、批量目标的差距结论

- **代码层面**：8 段流程全通，批量所需的「显式明细→批次→执行→逐条结果→验收→重做→导出」闭环完整。
- **运行层面**：**未达批量可用**。卡点是 P0 两项——GPU 可用性无保障、失败无自动重试。这两项不解决，「批量」在真实环境会持续需要人工盯着重跑。
- **建议下一步（按优先级）**：
  1. 决策 GPU 形态（包年包月 / 自有服务器 / 克隆兜底），消除 P0-1；
  2. 实现批次级自动重试 + 全局串行（消除 P0-2 与 P1-1）；
  3. 修轮询新鲜度校验（P1-3，防假成品）；
  4. 合并数据双轨（P1-4）；
  5. 再做一次真实批量 E2E（3–6 条）作为批量验收。
